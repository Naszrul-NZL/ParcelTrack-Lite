# Integration release and AWS operations plan

This plan joins the [three module plans](../project-plan.md) using the [shared system contract](system-contract.md). It defines future implementation/release work; no infrastructure, CI or application has been deployed by this document.

The [automated testing strategy](testing-strategy.md) defines required unit/component, API/PostgreSQL integration, browser and operational suites, feature traceability and CI/release gates.

## Shared foundation and handoff order

Delivery runs in six phases (PH1 to PH6) with group gates G1 to G6. The per-member milestone matrix is in the [phase framework](phase-framework.md#milestone-matrix-who-delivers-what-in-each-phase); every handoff, its proving test and its temporary substitute are in the [dependency matrix](dependency-matrix.md); the first tasks each member starts with are in the [execution sequence](execution-sequence.md).

Development may proceed against shared contracts and fixtures, but substitute authentication or in-memory persistence cannot remain in the final product: the labeled substitutes TMP-01 to TMP-05 are retired by named tasks before gate G3. Avoid three independent frontend/backend/database stacks. Each owner changes their module and contributes its migrations/tests; integration coordination does not replace individual authorship.

## Migration and configuration contract

Use one Alembic history with the fixed revision order in the [contract amendments](system-contract.md#migration-order-and-database-roles) and [dependency matrix](dependency-matrix.md#migration-and-layer-order). Modules name revisions descriptively; Zikri coordinates revision heads before merging. Do not rewrite an applied revision. Application schema, RLS policies, function ownership and grants belong in reviewed migrations, not manual GUI changes. The migration process uses a separate credential and runs once before application rollout, never at every worker startup.

Before Alembic, an idempotent operator-only cluster-bootstrap script (M2-PH1-T01, verified on cloud by M2-PH5-T01) creates the database and login/non-login roles: migration/owner, app_runtime, tracking_runtime, maintenance_runtime, ops_runtime and narrow function-owner roles. ops_runtime is private execute-only access to reviewed account incident-lock/recovery functions; it is not supplied to the web container. Passwords are injected privately, never defaults in SQL. Cluster role creation requires a separate bootstrap administration credential; Alembic does not discover or create its own privileged login. Define explicit ownership and membership so runtime, maintenance and operations callers cannot SET ROLE to migration/function owners. Bootstrap may provision the migration role's limited owner memberships so it can create/assign reviewed functions; remove its credential from long-running services after migration. On an existing volume, check expected roles without resetting credentials automatically. Restore uses the same reviewed role bootstrap before restoring grants.

Initial Admin provisioning (M1-PH5-T04) is the private idempotent `provision-admin` command (an `ops_fn_owner` function called with `ops_runtime`, built and tested in PH3, M1-PH3-T04) with a privately supplied password and `must_change_password` set; it can create the two Admins of the case study and a rerun for an existing username changes nothing. Synthetic fixtures use a separate test-only provisioning credential/job and never load automatically into production. Test provisioning may call domain functions under controlled contexts or seed using its dedicated test role; runtime credentials gain no direct DML just to make seeding easier. A second bootstrap/fixture run must not duplicate users or overwrite credentials.

Start a clean PostgreSQL database and upgrade to head in integration checks. Also test upgrading the previous released schema with synthetic data. Application credentials cannot create/alter schemas or migrate. On destructive changes, use an additive compatibility step and test recovery before removal. Do not run a blind downgrade on live recipient data.

Keep .env.example with names and inert placeholders only. Local .env files and real keys stay ignored. Required settings cover environment, application origin, app/tracking/migration/maintenance/operations DB credentials, cookie policy, session lifetimes, proof directory/limits, throttle limits, log level and trusted proxy addresses. Bootstrap, migration, maintenance and operations secrets are provided only to their intended jobs/commands, not the public API container. Frontend VITE settings are public build data and cannot contain secrets.

## Local and cloud topology

Docker Compose services: PostgreSQL, one-shot migration job, FastAPI backend, reverse proxy/static React host, and a scheduled maintenance runner using the same backend image. A configured scheduler is mandatory before final cloud release; the runner uses maintenance_runtime and cannot accept HTTP requests. Build the React bundle with locked dependencies; use a production server to serve it. Local development may run Vite with an /api proxy and source mounts; production has immutable application images and no source-code bind mounts.

AWS is the confirmed provider; one Linux EC2 instance is the proposed starting deployment. Region, account, sizing, budget and domain require real project values before provisioning. Provisioning is a later action, not authorized merely by recording an architecture. A single host is an intentional coursework deployment and has one host as a failure boundary.

The proxy publishes HTTPS and HTTP for redirect/certificate issuance as needed. FastAPI and PostgreSQL publish no public ports. If SSH is used, limit its source to team administrator IPs; otherwise use a configured AWS-managed administrative access method. Configure IPv6 rules consistently if enabled. [AWS security-group guidance](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/security-group-rules-reference.html).

Proxy /api/v1 to FastAPI, serve built React assets and return index.html for frontend routes only. Do not let SPA fallback swallow API 404s. Block /internal and private proof directories at the proxy. Health probes used by Docker run on private endpoints and reveal no credentials, SQL or internal paths. Trust forwarded headers only from the configured proxy; the proxy replaces client-supplied forwarding values.

PostgreSQL and proof data live on encrypted EBS-backed storage, using named volumes/mounts mapped to that durable disk. Explicitly review DeleteOnTermination behavior. Replacing a container must not delete its data volume. Separate app data from replaceable images. Backend, runner and proxy containers run as non-root users with read-only root filesystems, `cap_drop: [ALL]`, `no-new-privileges` and memory/process limits; the proxy sits on an `edge` network and PostgreSQL on an internal `data` network; credentials are mounted as files or Docker secrets, not plain environment variables; instance metadata is IMDSv2-only with hop limit 1; administrative access defaults to AWS Systems Manager Session Manager (no inbound SSH). Docker logs rotate (`max-size`, `max-file`) or ship to CloudWatch Logs with 90-day retention, and PostgreSQL runs with `log_statement='none'` and parameter logging disabled (`log_parameter_max_length=0`, `log_parameter_max_length_on_error=0`), checked by `verify_grants`. The proxy also applies request-rate and connection limits and header/body timeouts. [EBS persistence and encryption](https://docs.aws.amazon.com/ebs/latest/userguide/EBSFeatures.html).

## Deployment sequence and rollback

1. Run local/integration checks, review the PR and merge through the protected branch once configured. Tag or record the exact commit used for release; record image digests and migration revision.
2. For an existing deployment, take a recoverable database/proof backup before schema changes and confirm the last restore exercise succeeded. For an empty first deployment, there is no data to back up yet; establish the recoverable baseline in step 3 before accepting user data.
3. Build immutable images, supply secrets privately, start PostgreSQL and wait for readiness (automated by the first-boot script, M1-PH5-T04). Run/check the operator-only cluster bootstrap before the one-shot Alembic upgrade with migration credentials. A first deployment has no previous backup/restore exercise; establish and test the initial recoverable baseline after schema/bootstrap and before accepting user data.
4. Provision the initial Admin using the private idempotent command if absent, then start backend/proxy with health checks/restart policies and the expected schema revision. Production has no fixed demo credentials or automatic test-data seed.
5. Remove bootstrap/migration credentials from long-running services and verify access using only the normal app/tracking/maintenance roles. Prove empty-volume startup in CI and repeat startup against an existing volume.
6. Verify HTTPS/domain, secure cookies, CSRF, runtime DB role, RLS and private storage from the actual cloud stack.
7. Run the complete successful/Failed workflows and negative permission checks on synthetic data. Record the live URL and version only after they work.
8. Enable scheduled cleanup/backups and verify their first safe run. Record who receives job failures.

If a new app image fails but the schema is compatible, restore the last known-good image digest. Keep maintenance mode on (reads only) from the start of a schema-changing deployment until the post-deploy smoke test passes, so a rollback never discards acknowledged writes; schema changes follow expand-then-contract so the previous image runs on the new schema. If schema/data rollback is needed anyway, restore a tested matching database/proof backup. Preserve incident evidence, confirm consistency and re-run smoke/security checks before reopening. Do not keep accepting writes during a destructive restore.

## Backup and restore

Coordinator: Syauqi (M3-PH4-T07 local drill, M3-PH5-T02 to T04 on AWS); Zikri verifies database roles/RLS (M2-PH5-T05) and Naszrul verifies authentication after restoration (M1-PH5-T08). The coordination mechanism (shared advisory lock, exclusive backup lock, `system_state.maintenance_mode`) is specified in the [contract amendments](system-contract.md#backup-coordination-and-maintenance-mode-d-15). Proposed defaults are daily encrypted off-host backups retained for 30 days, with access limited to the recovery operators. Backups include PostgreSQL logical dump, database role/grant recreation information, private proof files, migration revision and an encrypted configuration recovery record. Never publish backup credentials or dumps in Git.

For the initial single-host project, use a short maintenance window: reject new mutations/uploads, pause scheduled writers/cleanup, drain in-flight transactions/uploads and acquire the backup/maintenance coordination lock before taking the matching database/proof backup. Stopping only new requests is insufficient while cleanup or earlier uploads are still changing files. Release the lock and resume workers after capture completes. Backups run as the operator-only `backup_operator` role (BYPASSRLS, never present in application containers), holding a session-level advisory lock for the whole dump and archive. Archives are encrypted on the host with a public key (age) whose private key is held offline by two named people, and stored in a private AWS S3 bucket (block public access, default encryption, no overwrite or delete for the instance role, lifecycle and noncurrent-version expiry at 30 days; EBS snapshots follow the same expiry or are not used). The recovery point objective is one backup interval: up to 24 hours of parcels, status changes and photos can be lost after a restore unless the team later adds WAL archiving. A successful upload alone is not a successful restore test.

Restore into a separate environment: recreate restricted roles, restore database and proofs, apply only compatible migration steps, restart the app and verify user login, five status counts, history, sample photos and RLS grants. Restore is data-only: bootstrap roles, `alembic upgrade` to the manifest revision, `pg_restore --data-only --disable-triggers` as the bootstrap administrator, then `verify_grants`, so policies and hardened functions come from migrations rather than from the dump. A dump taken without `backup_operator` is filtered by RLS and is not a complete backup. The restore exercise uses synthetic data, or a protected same-account environment limited to named operators and destroyed afterwards (D-38). Record observed restore time and backup age; do not invent availability or recovery guarantees.

Before reopening any restored environment, purge every restored auth_session row with the private `purge-sessions` command (M1-PH4-T05) and require fresh login. Reconcile disablements, lock operations and password changes made since the recovery point by replaying the off-database account journal (`reconcile-accounts --from-journal`, which re-disables accounts disabled since the backup and forces a password change for accounts whose password changed since); web-path events such as Admin disablement are in the journal as well as the database. If the journal is unavailable run `quarantine-after-restore` (disable every Rider, force a password change for all accounts) and have an Admin re-enable against the staff roster. Keep uncertain/affected accounts locked and reset credentials privately. A restore after compromise also rotates affected service/operator secrets. Test with a cookie that existed in the backup but was logged out/revoked later: it must remain unauthorized after restore. Normal container restarts may preserve unexpired sessions, but database restore never revives old sessions.

Retained backups are not used to restore expired personal data into service. After any restore, run retention anonymization and deny expired proof access before reopening. The proposed 30-day backup expiry must be documented with the project's P3 interpretation; remove expired backup copies through lifecycle rules.

## Retention jobs and incident response

Daily maintenance includes anonymization/proof deletion, stale unreferenced upload cleanup, and expired session/rate-bucket cleanup. Jobs use a lock so two copies do not process the same batch concurrently. Process small batches, log counts/opaque IDs without recipient details, and retry interrupted cleanup idempotently. The maintenance role can execute reviewed cleanup functions only and has no web-exposed entry point.

Incident coordinator: current Admin, with Naszrul as initial team contact. The actual contact channel must be recorded privately before cloud release. Anyone noticing a suspected breach reports it within one hour as required by P5. Admin disables affected accounts, invalidates sessions, preserves safe logs, restricts access if needed, investigates the cause, rotates affected credentials and tests the fix before restoring access. Do not erase evidence or place recipient data/passwords in incident reports.

M1 supplies a private operator-only lock-account command for any role, including a compromised Admin; A09 remains limited to Seller/Rider targets. The command disables the account, increments session_version, revokes sessions and records a protected audit event. A separate private recovery command verifies operator authority, privately resets credentials when necessary and reactivates only after investigation. These commands use a narrowly granted operational function/credential, never a public endpoint or an owner bypass. Document access to this operational credential so a single locked Admin cannot prevent recovery. Test Admin lock/recovery and old-cookie rejection.

## Release acceptance and final submission

Run API/DB tests for authorization and transactions, and browser tests for actual forms/navigation/privacy. Exercise mobile-width Rider screens and keyboard operation. Use synthetic users, parcels and harmless image fixtures. UI mocks are useful during development but do not count as integrated acceptance.

Use the source's expected scale as a capacity-check baseline: about 50 Sellers, 15 Riders, 2 Admins and 800 parcels per day. Test list/search/dashboard queries with a representative synthetic history, verify pagination/index usage, and record actual response times on the chosen EC2 instance. Test slow/interrupted mobile requests and observe memory during image validation. Do not claim the chosen instance can sustain a load until measured.

The final security document records each module owner's name, test input, expected result and actual result, with safe evidence and app/environment version. More than five input types per member must be tested and documented for the highest rubric testing band. Any failed required test stays open; do not convert a planned outcome into a pass.

Rehearse approximately 10 minutes per member, 30 minutes total: demonstrate required functions, show failed attacks live, explain own code and answer questions. The cloud URL must work for every role. Include deployment, restore and policy evidence in the group handoff. No calendar date is inferred for Week 14.

For the 22 October checkpoint, report the PH2 slices and prepared design truthfully (gate G2). The complete plan does not make implementation complete. Update the [phase status board](phase-framework.md#phase-status-board) with actual evidence as each phase finishes.
