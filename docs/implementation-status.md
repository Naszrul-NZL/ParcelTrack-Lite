### Foundations (draft)

**Revision `0008_account_functions` is registered** (0006 and 0007 are on `main`): `register_account`, `change_password`, `set_user_active` and `admin_reset_password`, the 72-hour `credential_expires_at` column, `get_login_snapshot` reporting `credential_expired`, and the directory and audit indexes. Shared request schemas for A06 to A09 and A20 are in `src/shared/schemas.ts` with unit tests. **A09 `PATCH /admin/users/{userId}/status` is implemented (M1-PH3-T02, handoff H31 for the assignment screen).** Admin only; body `{isActive, expectedVersion}` (strict, bounded JSON with a five-second read deadline, version limited to a database integer); Seller and Rider targets only (`403 TARGET_NOT_ALLOWED` for an Admin or the caller, `404` for an unknown or malformed id, `409 VERSION_CONFLICT` for a stale version). A disablement or reactivation bumps the account's versions and deletes its sessions, so the old cookie fails on its next request and reactivation does not restore it; it is audited as `USER_STATUS_CHANGED`. It goes through the protected transaction, so CSRF, same-origin evidence and the maintenance gate apply. Evidence: `tests/integration/admin-user-status.test.ts` (8 tests, TC09, TC11 and TC22 for this endpoint) and the A09 matrix row; the whole isolated integration project passes. The shared `readJsonBody` helper (`src/server/core/json-body.ts`) is the bounded-body reader for the remaining JSON endpoints. **A02 `POST /auth/register` is implemented (M1-PH3-T03).** Public; needs the CSRF token from A01 (the anonymous session). Strict `{username, displayName, password}`: the username is normalized, so `ALICE` collides with `alice` (`409 USERNAME_TAKEN`), and any extra field such as `role` is a 422. The role is fixed to Seller inside `register_account`, the password policy and common-password list apply (`fieldErrors.password`), the hash is Argon2id and never echoed, logged or audited, and the response is the Seller's `Principal` with no cookie (no automatic sign-in). Attempts are limited per source address (`REGISTRATION_LIMIT_PER_HOUR`, default 30, validated to 1 to 1000) and a refused attempt creates nothing. It is a business write, so the maintenance gate applies. Evidence: `tests/integration/auth-register.test.ts` (8 tests covering TC01 to TC05 plus CSRF and maintenance), the A02 matrix row and a unit test for the setting; the whole isolated integration project passes (119). **A06 `POST /auth/password` is implemented (M1-PH3-T06).** A signed-in account changes its own password, and an account that must change it may call it. Strict `{currentPassword, newPassword}`; the new password must differ from the current one and meets the policy and common-password list (errors are reported on `newPassword`). Wrong current-password attempts are limited per account (5 per 15 minutes; the sixth is refused even with the right password) and are counted separately from login failures. On success `change_password` replaces the hash under the account lock, compares the hash that was verified so a concurrent change cannot be overwritten, clears the must-change flag and credential expiry, bumps both versions and deletes every session of the account, the caller's included; the response is 204 with the cookie cleared and nobody is signed in again. It is a business write, so CSRF, same-origin evidence and the maintenance gate apply. Evidence: `tests/integration/auth-password.test.ts` (7 tests: TC06, TC07, must-change, validation, CSRF, a simultaneous-change race, maintenance and a disabled account) and the A06 matrix row. The PH3 worksheet rows M1-08, M1-09 and M1-10 now have recorded results. The endpoints still to build are A08 and A21, then the audit viewer (A20) and the screens.

**A10 creation is replay-safe (M2-PH3-T01).** Repeating a client request ID with the same canonical data (trimmed fields, normalized phone, three-place weight) returns the original parcel with `200` and writes nothing; different data is `409 IDEMPOTENCY_CONFLICT`; a key whose parcel was anonymized is `409 REQUEST_EXPIRED` and recreates nothing. The unique constraint decides simultaneous requests, so both callers get the one parcel. The fingerprint is HMAC-SHA256 keyed by `FINGERPRINT_KEY`, never a plain hash. The registration page keeps one request ID per intended registration and explains both 409s. Evidence: `tests/integration/parcel-replay.test.ts` (TC01), `tests/unit/parcel-fingerprint.test.ts` (TC02) and a component case in `tests/component/seller-parcels.test.tsx`; the earlier PH2 duplicate case now expects the replay.

**A11 search, filter and sort (M2-PH3-T02).** `q` (1 to 64 characters, trimmed) matches a tracking-number prefix or a recipient-name substring, case-insensitively and literally: `\`, `%` and `_` are escaped, so they match only themselves. `status` takes one of the five statuses, `sort` is `createdAt` (default, newest first) or `currentStatus` (delivery stage, then newest first), always with the id tie-break; unknown, repeated or invalid parameters are 422. The SQL text stays constant. Evidence: `tests/integration/parcel-search.test.ts` (TC03, TC04, TC15). No new index: the Seller's rows are already narrowed by `parcel_seller`, and EXPLAIN at scale is PH4 work. The search UI is M2-PH3-T07.

**Revision `0009_tracking_lookup` (M2-PH3-T04).** `app.lookup_tracking(token)` is owned by `lookup_fn_owner`, runs with the fixed `pg_catalog, app, pg_temp` search path and is executable only by `tracking_runtime`. It matches the token exactly and returns only `status` and `changed_at`, ordered by time and then history id. `src/server/modules/parcels/tracking.ts` calls it through the separate `tracking_runtime` pool after asserting the connected role, and parses the result through the public allowlist schema. Evidence: `tests/integration/tracking-lookup.test.ts` (TC06: exact match only, no table or other-function access for `tracking_runtime`, catalog owner/search path/grants, and hostile `pg_temp` tables ignored). The A13 route, its limiter and the `/track` page are M2-PH3-T05 and T06.

**Revision `0010_retention_functions` (M2-PH3-T08, handoff H36).** `list_retention_candidates(batch, as_of)` and `anonymize_parcel(parcel_id, as_of)` are owned by `maintenance_fn_owner` and executable only by `maintenance_runtime`, so no web or tracking role can call them or choose `as_of`. A parcel is due 12 calendar months (in UTC) after `terminal_at` when DELIVERED or FAILED (D-06), or after its last status change when it never became terminal (D-31); it is due at that instant exactly, and 29 February plus 12 months is 28 February. `anonymize_parcel` re-checks the rule under the row lock, clears the recipient fields and creation fingerprint, sets `anonymized_at` to the server time, bumps the version and audits `RETENTION_ANONYMIZED` with no actor; history, proof metadata and the tracking number stay, and a second call returns `false` without another audit row. The revision grants the owner `INSERT` on `audit_event` and `SELECT(parcel_id, changed_at)` on history with a read policy; this is a privilege change, so all three owners approve it. Evidence: `tests/integration/retention.test.ts` (TC12 boundaries at minus one second, exact and plus one second, a leap day, a session time zone that would shift the date, terminal and non-terminal parcels, batch and input checks, catalog and denied web/tracking callers; TC13 single anonymization, unchanged public tracking, the anonymized A12 view and `REQUEST_EXPIRED` for the old creation key). The tests sign in as `maintenance_runtime` with its generated local password. Scheduling (M2-PH4-T03, H33) and the proof purge that reads `anonymized_at` (M3, H46) are later work.

**A13 public tracking (M2-PH3-T05).** `POST /public/tracking` needs no session or CSRF token but rejects a foreign or missing origin. It charges the per-source limiter (30 per minute, keyed by an HMAC digest; malformed bodies and invalid tokens count) before reading the body, trims and uppercases the token, answers `422` for a bad format and a uniform `404` for an unknown token, and returns exactly `{history:[{status,changedAt}]}` with `no-store` through the `tracking_runtime` pool. `tests/integration/public-tracking.test.ts` covers TC07, TC08 and TC19; the authorization matrix has an A13 row.

**`/track` (M2-PH3-T06).** The page posts the normalized number with no cookie, CSRF token or referrer, shows Malaysia time, and gives distinct messages for 404, 422, 429 (with the wait), server failure and network failure while keeping the typed number. Only the latest lookup can update the screen. Nothing is stored and real numbers never enter the URL. The synthetic sample journeys remain, clearly labelled, and never send a lookup. Component tests cover TC10; `tests/e2e/public-tracking.spec.ts` covers TC09 on the real stack for Registered and Assigned parcels (the API test covers all five statuses and an anonymized parcel).
